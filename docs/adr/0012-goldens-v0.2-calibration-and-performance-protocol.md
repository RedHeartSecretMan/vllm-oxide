# Bind goldens-v0.2 calibration and performance evidence

Ticket #45 must turn GPU observations into release evidence without recreating the legacy loop of raising a tolerance until the same data passes. Its issue fixes the required outcomes, but not the exact oracle kernels, empirical approval boundary, benchmark formulas, report ownership, or candidate-bound publication order. Those choices change what counts as acceptance and therefore belong to the DAG Definition.

## Two-checkpoint tolerance approval

The first Rust GPU comparison is a **Calibration observation**, not an acceptance run. Its readable candidate subset is exactly `canonical_01`, `canonical_02`, `canonical_03`, and `canonical_05a`; the sealed holdout is exactly `canonical_04`, `canonical_05b`, `canonical_05c`, and `canonical_05d`. Both `l1_near_tie_max_abs_logit_gap` and `l2_atol` are zero, the command labels the policy pending, and the stage exits non-zero even if every calibration value happens to match exactly. The observation tool refuses to open candidate logits or tokens for a holdout fixture and records the exact fixture IDs it did open. Baseline-versus-reference evidence may cover all 28 baseline cases for investigation, but no baseline statistic is an input to candidate threshold selection.

For every readable calibration case and aggregate, the observation records candidate-versus-reference same-prefix row/element counts, first divergence, candidate expected-versus-selected token gap, mean and RMS absolute error, p50/p95/p99/p99.9 absolute error, maximum absolute error, non-finite count, and the exact fixture, binary, environment, and kernel identities. Shape, coverage, identity, or non-finite failures invalidate the observation rather than becoming distribution samples. Every finite shape-valid same-prefix element and every actual divergence from all four calibration cases participates; root-cause review may require a code repair and complete rerun but may never discard or relabel a sample out of the maximum. Following the bounded, evidence-backed revision in [ADR-0013](0013-bf16-cross-kernel-calibration-ceilings.md), the L2 selection ladder is `0` followed by powers of two from `2^-12` through `2^0` inclusive; the proposed L2 value is the smallest ladder member that covers the complete repaired calibration-run maximum and can never exceed `1.0`. The L1 near-tie ladder is `0` followed by powers of two from `2^-12` through `2^-3` inclusive; its proposal is the smallest member that covers every candidate token gap at an actual calibration divergence and can never exceed `0.125`. These are calibration ceilings, not approved acceptance tolerances. No divergence means an L1 value of zero; an exactly matching L2 run means an L2 value of zero. Exceeding either ceiling blocks policy approval and requires a correctness investigation; it does not authorize another automatic ceiling increase.

After root-cause analysis, Ticket #45 pauses again. The Coordinator may approve the one mechanically proposed pair only through a second DAG Definition Revision that adds a normalized calibration observation record to the Definition, records its blob and raw-evidence SHA-256, explains each accepted error class, and receives fresh independent review. The vLLM legacy `2 × max` value remains evidence only and is never copied automatically. Only after that checkpoint may the candidate comparator open the four holdout fixtures and run the authoritative comparison across all eight full-logit cases and all 28 L1 cases. If a holdout or authoritative comparison fails, a threshold is not raised from that result; code/root cause must be repaired, or a new disjoint holdout corpus and protocol must be approved through another Definition Revision.

L1 accepts only an exact reference token or a near-tie whose candidate-logit gap is within the approved bound at the first divergent same-prefix row. Regression cases without full logits remain exact-token only. L2 remains absolute-tolerance-only, includes the first divergence row, and excludes every later row.

## Reproducible performance baseline

Performance is evidence, not a cross-hardware gate or a vLLM parity claim. It runs only after the empirical tolerance Definition Revision completes and the authoritative comparison has opened and passed the sealed holdout. It measures the Rust candidate without raw-logit capture. A private release-tooling telemetry mode may be added behind the existing default-off `internal-golden` feature, but it adds no public Rust item and normal generation remains unchanged. When active, CUDA is synchronized at measured step boundaries and only small timing/identity records cross to the host.

There are two workloads: `canonical_04` as one request and the four `canonical_05` prompts as one batch. Each uses greedy sampling, `ignore_eos=true`, exactly 64 completion tokens per request, the fixed Rust `EngineOptions` above, and a cold request/prefix-cache state. One throwaway run per workload primes runtime kernels but is not reported. Each of three measured repetitions constructs a fresh `LLM`, excludes construction and its built-in warmup, then executes the workload once; all raw samples are retained and the median is the headline.

The admission timestamp is taken immediately before the first request enters the engine, after tokenization. A sampled-token timestamp is the synchronized end of the step that selected it. Prefill throughput is the number of newly executed uncached prompt tokens divided by the summed synchronized duration of steps containing prefill work. Decode throughput is the number of completion tokens after each request's first token divided by the summed synchronized duration of steps emitting those post-first tokens. Time to first token is admission to the first sampled-token timestamp for each request. Per-token latency is the per-request interval between consecutive sampled-token timestamps and reports mean, p50, and p95 as well as every sample.

Peak memory is device-wide used GPU memory sampled at most every 50 ms from the post-initialization baseline through the final synchronization. The report records baseline, maximum, delta, polling interval, sample count, and other compute processes; an unavailable or interrupted monitor invalidates the repetition. No unrelated CUDA compute process may be active at stage start.

## Evidence and publication

Machine outputs, raw observations, fixtures, and bundle staging remain under `/tmp/vllm-oxide-dag-v0.2.0/t45-artifacts`. Before authoritative GPU work, Ticket #45 freezes a reviewed **measurement commit** containing every executable, schema, and workflow byte used by generation, comparison, and benchmarking. The Ticket then commits `docs/releases/goldens-v0.2.md` as the **Golden release evidence report** in a descendant evidence-only commit. The report records the measurement commit and tree, environment and kernel paths, 56/28 lifecycle totals, approved tolerance and observation identity, all performance samples and headline medians, limitations, `manifest.json` SHA-256, and `goldens-v0.2.tar.gz` SHA-256. It does not claim to contain its own final commit or tree. The diff after the measurement commit may change only the report and other explicitly reviewed non-executable evidence; any executable, manifest-schema, prompt, fixture, or workflow byte change invalidates the measurements and requires a new measurement commit and GPU evidence.

The resulting descendant is the final Promotion Candidate and eventual tag target. Its identity is recorded by the DAG transition, Git tag, and GitHub Release metadata outside the report, avoiding Git self-reference. The report is not a third release asset. The GitHub Release body mirrors its summary, names both the measured commit and final tagged commit, and links the tagged tree.

Publication is a separately authorized final stage. After the exact Ticket candidate, report, manifest, archive, checksums, clean-consumer verification, and fresh review are frozen, the full `refs/tags/goldens-v0.2` must be absent. With explicit user authority, one non-forced tag push points that tag directly to the frozen Ticket candidate; no remote Ticket branch is created. A `goldens-v0.2` GitHub Release for that exact tag then publishes exactly `manifest.json` and `goldens-v0.2.tar.gz`. Remote tag, release metadata, exact asset names, downloaded bytes, checksums, manifest validation, and archive contents are read back before DAG promotion. Existing, partial, conflicting, or failed publication leaves Ticket #45 unaccepted and is never overwritten, force-updated, deleted, or repaired without new authority. The product `v0.2.0` tag and release remain Ticket #47 work.

GPU-owning stages are serial and use fresh processes so device memory returns before the next owner starts. Rust compilation uses `/home/wanghao/Projects/Codes/VibeCodings/vllm-oxide/target` with one build job and must reuse the existing FlashAttention cache. Available host RAM below 16 GiB stops the active stage. Oracle generation and benchmark stages record disk, RAM, and GPU guards before and after execution.
